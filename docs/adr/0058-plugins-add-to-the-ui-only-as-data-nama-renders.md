# Plugins add to the UI only as data Nama renders

Jellyfin's most popular UI plugins inject JavaScript through File Transformation and break on every release, and their pages stop looking like Jellyfin. So a Plugin adds to Nama's web app only by answering, with data, at an Extension Point the Kernel serves, and Nama draws every pixel and word around it; a Plugin never supplies JavaScript, HTML, CSS or an iframe. Each place in the UI is an ordinary Extension Point, one contract service with its own version (ADR 0043), with no umbrella "UI Extension Point". The first is the Home row: work on it waits until Continue Watching (#882, #904) and Library browse (#884) settle, so its contract isn't fixed around a home page still moving.

A Plugin serving the Home row point answers ahead of time, not while a page loads. It may serve two optional exports, and serving one is its declaration: `shared_rows`, called with no User, gives rows every User sees, such as "Trending this week"; `user_rows`, called for one User with their Personal settings, gives that User's own, such as "Your Trakt watchlist". A Plugin serving only `shared_rows` is never called per User. Each answer lists up to 3 rows, each with a stable key, a plain-text heading of at most 40 characters, a time to live the Kernel clamps to between 15 minutes and 1 week, and up to 200 External IDs; the Kernel cuts what goes over. The Kernel stores the rows and the web app reads only what's stored, so home never waits on a Plugin. When a User opens home, rows past their time to live are refreshed in the background, one refresh per Plugin and scope at a time, and so are a Plugin's shared rows when it is enabled or its settings change; the page shows the stored rows meanwhile, and a Plugin's first rows appear on a later load. A refresh is a long call, on its own compile like other long calls; one that fails keeps the rows it had, and counts toward disabling the Plugin like any failed call. A refresh replaces that Plugin's rows for that scope in one transaction, so nothing accumulates: stored rows are bounded by Plugins, Users, 3 rows and 200 titles, deleted with their User and when their Plugin is disabled. Clearing a User's rows who stopped visiting is #1005.

The Plugin sends only External IDs, never names, posters or URLs. At refresh the Kernel resolves a missing title through the Server's title sources, as a Request does, and stores its name, year and poster path with the row, dropping what it can't resolve; the poster is proxied, never stored, like any looked-up title's. Whether a title is on the Server, its Request state and the reader's Request Permission are read live, so a title a Scan adds turns playable without a refresh. So the browser never loads from a host a Plugin picked, and every title looks like every other. A row may hold missing titles, which the User can Request from them, so a discovery row can be a Plugin; for a User without the Request Permission the Kernel drops them, and a missing title with an open Request shows its state. PRODUCT.md's first principle names this exception. The web app reads each row on its own with `nama.v1.PageRequest` and `PageResponse` (`proto/nama/v1/page.proto`, ADR 0055), keyset over the stored rows. The Kernel's rows come first, then each Plugin's in Plugin id order, since the Kernel records no enable order. A Plugin's failures show in the log and on the Plugins page, never on the home page.

## Considered Options

- **No UI extension**: rejected. Home Sections and Custom Tabs show the demand, and without a declared point it moves to forks and injection.
- **Plugin-supplied JavaScript or iframes**: rejected. It repeats Jellyfin's breakage, lets a Plugin run code in every User's session, and gives up PRODUCT.md's look and words.
- **Only titles on the Server in a Plugin's row**: rejected. A discovery row is wanted, and Requests are part of browsing; dropping missing titles for Users who can't Request keeps them from dead ends.
- **Asking Plugins while home loads**: rejected. Every page view would wait on outside services under a short timeout, a timeout would interrupt the Plugin's other calls, each missing title would cost a title-source lookup per view, and the Kernel would have to wrap Plugin page tokens.
- **Refreshing every User's rows on a schedule**: rejected. It pays for Users who never open home; refreshing on a stale visit pays only for readers.
- **A Manifest flag for shared or per-User rows**: rejected. Which optional export a Plugin serves already says it.
- **Plugin-supplied names and posters**: rejected. The browser would load from hosts the Admin never granted, and a Plugin could show anything under a title's name.
- **Admin pages from a Plugin-supplied schema**: dropped. Plugin settings and Personal settings (ADR 0046) already render from the Manifest; a further admin point waits for a Plugin they can't serve.

## Consequences

- Admins ordering rows, and Users reordering and hiding any row, Kernel or Plugin, is #999.
- A title-page panel (text, links, the Request action) is the likely next point; it gets its own decision when a Plugin needs it.
