# Recognisers propose what a file is; the Kernel decides

The Kernel's Matching reads a file's name and searches the Library's title sources. It can't read every naming scheme: an anime Episode numbered from the start of its Show, such as `Show - 137.mkv`, has no `SxxEyy` or `1x02`, so the name parser makes no Item from it and it is stored as an unparsed file the Matching never sees. A Recogniser is the Extension Point for that knowledge, `nama.plugin.v1.RecogniserService`, with the Built-in `Recogniser` trait mirroring it. It is named apart from the code's `matching::Matcher`, which fixes Matches by hand. Both of its methods are optional, behind the table-driven adapter (ADR 0043), so one point serves a Plugin that reads file names, one that knows titles, or both.

A Recogniser only proposes. The Kernel owns every Match, which Contents writes, and the Unmatched decision, and its own Matching stays the Built-in default it falls back to. It asks at two levels:

- **Title level** (`recognise_title`): for an Item, the Kernel tries a pin, then an ID Hint, then the title sources' search with its year-less retry. Then it asks each Recogniser in order with the Item's kind, name, year, paths and the search's final candidates. The first to propose ids with a namespace one of the Library's title sources serves wins, and the Kernel fetches the title as it does for an ID Hint. If none does, `confidence::decide`'s decision stands, except that for a Show it ties, the one tied Show that alone has every Season and Episode the Item's files name is the Show.
- **Unread files** (`recognise_file`): the Kernel asks each Recogniser in order about a file the name parser makes no Item from, with its path relative to the Library's folder and the Library's kind. The first proposal, a Movie with a title, year and any ids, or a Show's title, year, Season and Episode numbers, becomes Items the Kernel then Matches as usual.

An empty answer means the Recogniser can't tell, and the Kernel asks the next one. A Recogniser that fails leaves the Item or file undecided for the next Scan, as a failing title source does (ADR 0044), so a Recogniser being down never stores an Unmatched it would have decided otherwise. Unlike a failing title source, it doesn't stop the rest of the Scan: the failure stays with the one Item or file, and Matching goes on with the Library's other titles and its refresh.

The Kernel asks on a new or changed file, and once for a Library's Unmatched and unparsed files when its Recognisers change: one is enabled or the Library's order of them changes. Nothing else already matched is re-decided. The Scanner decides this at the start of each scan, so enabling a Plugin never calls up the rows into the Scanner: `libraries.recognisers_read` keeps the Recognisers the Library listed that were enabled, in order, when its last scan started. A scan that finds them different marks the Library's unparsed files to be read again, as a name parser version bump does (ADR 0023) but for this Library alone, forgets its automatic Unmatched decisions, and stores the new list, in one write; pinned and Matched Items are untouched. The scan then reads those files, asking the Recognisers, and Matching decides the Items again. Updating a Library's order already queues a scan, so a new order takes effect at once; enabling or disabling a Recogniser takes effect at the Library's next scan, such as the six-hourly one or one an Admin starts with `ScanLibrary`.

Each Library holds its Recognisers in an order the Admin sets, stored and shown as its title source order is (ADR 0044): `libraries.recognisers` keeps the Plugin ids comma-separated, and the client API's `Library.recogniser_ids` sends them. The Kernel asks only the Recognisers a Library lists that are enabled, in its order; the Admin's precedence between Providers plays no part. A new Library lists none, and every Library from before keeps none, so an Admin lists a Recogniser on each Library that should use it: enabling one changes nothing until a Library names it. An update that leaves `recogniser_order` unset keeps the Library's order, and one that sets it with no ids clears it, so a client built before this keeps working. The Server refuses an id of no Plugin whose Manifest names the Recogniser point, or one named twice, with `REFUSAL_REASON_RECOGNISERS_INVALID`; `ListPlugins` marks the Plugins a Library may name with `EXTENSION_POINT_RECOGNISER`.

## Considered Options

- **One Extension Point per level**, a title recogniser and a file recogniser: rejected. Both levels serve the same knowledge of a naming scheme, and optional methods on one point let a Plugin serve either or both, as a title source serves only some of its methods.
- **One Server-wide order**, the Admin's precedence between Providers: rejected. A Recogniser for one naming scheme, such as anime's, would be asked about every Library's files, and an Admin couldn't keep it off a Library whose files it misreads.
- **Recognisers writing Matches**: rejected. The Kernel would lose the one place that decides a Match and what is Unmatched, a pin could be overwritten, and a failing or wrong Recogniser could leave a Library in a state no Admin chose.

## Consequences

- The contract adds `RecogniserService` 1.0.0 and `CONTRACT_VERSION` takes a patch bump; a Plugin built before it is unaffected.
- A Recogniser's title-level proposal is only as good as the Library's title sources: ids in a namespace none of them serves are ignored.
- Files already matched stay as they are when a Recogniser is enabled; only Unmatched and unparsed files are asked again. A Recogniser disabled before one scan and enabled again before a later one changes the list twice, so each of those scans reads them again.
- A Recogniser does nothing for a Library that doesn't list it, so a Plugin for anime names never touches a Movies Library the Admin keeps it off. A Library's order outlives its Plugins: an id whose Plugin is disabled or removed stays listed and is skipped until it comes back.
- A Recogniser that keeps failing stays enabled but isn't silent: its Plugin page shows its last error, when, and how many calls in a row failed, until a call answers (`plugins/failing.rs`, in memory, so a restart or disabling it clears it). A scan logs each failing Recogniser once with how many files it failed on; Matching logs only the first failure of a run.
