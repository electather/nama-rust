# The Kernel owns Users, Devices and sessions; Plugins only check credentials

Users, Devices and their sessions are Kernel state (ADR 0006 lists auth sessions in the Kernel). How a person proves who they are is a Provider: the `local-auth` Built-in Plugin checks passwords, and in M5 the Hub becomes another one. A Provider answers only "these credentials belong to this User". It never issues or checks sessions, so every client and every route authenticates the same way, whichever Plugin signed the User in. Plugins have no storage of their own, so the Kernel keeps each of a User's Sign-in Methods as a row holding the Plugin's id, an optional subject (an outside provider's id for the person, or a passkey's credential id, by which the Kernel finds the User) and an opaque credential that only that Plugin can produce and check (for `local-auth`, an argon2id hash). A User can have several Sign-in Methods, at most one of them a password, and always keeps at least one way in. A Link to a Hub Account is not a Sign-in Method: it carries Watch State sync as well as sign-in, a User has at most one, and Hub sign-in finds the User through it. The table and column names follow better-auth's (`provider_id`, `username`, `expires_at`, `ip_address`, …) where they don't clash with the Glossary, so `accounts` is `sign_in_methods`, its `account_id` is `subject`, and `sessions` stays `devices`.

A Device's session is an opaque random token, stored hashed and deleted to revoke the Device. Browsers send it as an HttpOnly cookie, because a `<video>` range request can't carry an `Authorization` header, and native clients send it as a bearer token. Both resolve to the same Device.

Changing a password, a Sign-in Method, or another User's Role or password needs the Device to have authenticated in the last 10 minutes. A Device that hasn't re-authenticates with any of the User's Sign-in Methods, which refreshes that Device instead of issuing a new session. A Device signed in by a Sign-in Code never proved anything itself, so it starts out needing to.

## Considered Options

- **JWTs for Server sessions**: rejected. A Device must be revocable at once, which a self-contained token can't do without a denylist. Hub-signed JWTs (ADR 0011) are only presented to a Server to start a session, never used as one.
- **Signed media URLs**: rejected. A second credential just for `/media/...`, and one that leaks through logs and shared links.
- **One credential-checking trait for every kind of Provider**: rejected for now. Password sign-in finds the User by name, while Hub sign-in carries a Hub-signed JWT and finds the User through their Link. `local-auth` implements a password-only trait, and the Hub gets its own trait in M5. Both only answer "these credentials belong to this User".
- **better-auth's `accounts` with typed columns** (`password`, `access_token`, `refresh_token`, …): rejected. Its plugins own their tables, ours have none, so only an opaque credential fits, and a Server needs a person's identity from an outside provider, not access to their data there.
- **Asking for the current password before a sensitive change**: rejected. A User who signs in only with a passkey or an outside provider has none.
