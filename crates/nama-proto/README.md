# nama-proto

Rust types and ConnectRPC stubs for the Nama API, generated from the schema in [`proto/`](../../proto) (ADR 0007).

Each proto package is a module. For `nama.v1` that is `nama_proto::nama::v1`, which holds:

- the message types, such as `GetServerInfoRequest`, generated by [buffa](https://github.com/anthropics/buffa);
- the service traits a Server implements, such as `ServerService`, and the clients that call them, such as `ServerServiceClient`, generated by [connectrpc](https://github.com/connectrpc/connect-rust). They are behind the default `connect` feature.

`nama.plugin.v1`, at `nama_proto::nama::plugin::v1`, holds the messages the Server and its Installed Plugins exchange, such as the `Manifest`. An Installed Plugin is built for wasm32, where the ConnectRPC stubs don't build, so `nama-pdk` turns `connect` off.

`NAMA_API_VERSION` is this crate's version: the Nama API version an Installed Plugin's `Manifest.nama_api` requirement is matched against.

## Why buffa and not prost

`connectrpc` requires buffa messages. Its service stubs decode requests into buffa's zero-copy views and encode buffa's JSON mapping, so prost types can't be plugged into it.

## Generated code is checked in

The code under `src/generated/` is written by `buf generate` and committed. The alternative was generating it in a `build.rs` with `connectrpc-build`. We check it in because:

- Building the workspace, or depending on this crate from another project, needs no protoc, Buf or codegen plugins on any platform.
- Every schema change shows up in review as a diff of the Rust API it produces.
- The `proto` CI job regenerates the code and fails if it differs from what's committed, so it can't drift from the schema.

Don't edit `src/generated/` by hand, and don't let rustfmt touch it. `src/lib.rs` marks the generated modules `#[rustfmt::skip]` so `cargo fmt` leaves them as `buf generate` wrote them.

## Regenerating after a schema change

Install Buf and the three codegen plugins, at the versions pinned in CI (`.github/workflows/ci.yml`):

```sh
cargo install --locked protoc-gen-buffa@0.9.2 protoc-gen-buffa-packaging@0.9.2 connectrpc-codegen@0.9.0
```

Then, from `proto/`:

```sh
buf lint
buf format -w
buf generate
```

`buf generate` empties `src/generated/` before writing to it, so deleted protos leave nothing behind. When you upgrade `connectrpc` or `buffa` in `Cargo.toml`, upgrade the plugins to the same minor version and regenerate.

## Breaking the schema on purpose

CI runs `buf breaking` against main and fails a change that breaks the schema, such as changing a field's type or moving it into a oneof. To make such a change on purpose, add an entry to the top of [`proto/BREAKING.md`](../../proto/BREAKING.md) in the same change, holding what the top of that file lists. CI then prints the breaks and passes (ADR 0032).

To see what CI will report, run from the repo root:

```sh
.github/scripts/buf-breaking.sh origin/main
```

It prints each break by file, and passes once the entry is there. For each break's rule, which the entry names, run `buf breaking --against '../.git#ref=origin/main,subdir=proto' --error-format json` in `proto/` and read `type`.
