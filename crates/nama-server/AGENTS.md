## nama-server

### Data

- **One database writer.** Every write goes through `Database::write` or `Database::write_then` in `src/db.rs`, on the one writable SQLite connection. Long jobs such as a scan write in small batches.
- **One owner for Server settings.** Only `src/server_settings.rs` reads or writes `server_settings`, tests included.
- **One owner for Plugin changes.** Outside tests, only `src/plugin_settings.rs` enables or disables a Plugin or saves its settings, under its one lock and in ADR 0028's order. The type enforces it: only Plugin settings and startup hold the `Registry`, and every other module holds its `ExtensionPoints`, which calls Plugins but can't enable, disable or list them. Handlers and tasks ask `PluginSettings`.
- **Migration list.** A new migration's file name also goes as the last line of `migrations.txt`, so two PRs adding the same migration number conflict in git (#561); a test checks it.
- **Query data.** After changing a `sqlx::query!` or anything in `migrations/`, regenerate `.sqlx/` at the workspace root and commit it (commands in `README.md`).
- **Config schema.** A change to `Config` regenerates `docs/nama.schema.json`, which editors check `nama.toml` against: `tests/config.rs` rewrites it and fails until it's committed.
- **Whole-Library reads.** Browse reads a Library's whole contents even to find one title. Each such read is marked `// ponytail: whole-Library read`; query by id there once Libraries get big.

### Security

- **Secrets stay out of storage and logs.** The database holds the Authenticator's credential string and the SHA-256 hash of each session token; only `src/users/passwords.rs` derives the credential, and `src/users.rs` the token's hash. Types holding a token or Sign-in Code skip `Debug`. The Setup Code is the one secret logged, on purpose. Plugin settings are the one secret stored as written, since a Plugin must send a key such as TMDB's as it is: no setting value is ever logged (the `Debug` of `SettingValue` and `PluginTables` hides them), and a secret's value, stored or default, is never sent to a client (`setting_to_proto` in `src/api/plugins.rs`).
- **Clients name ids.** Media is served by Version id (`Contents::version_file`), an image beside the media only as a copy some Version's row records (`Contents::local_image_type`), and artwork only for paths some Match stores (`Contents::stores_image`) or a Movie or Show search, lookup or artwork list handed out (`Artwork::offer`), and a Custom Image is picked only from those, downloaded through its title source (`Artwork::offered_bytes`). Where a Library lives on disk is shown only to Users with `MANAGE_LIBRARIES`, except that a User with `DELETE_MEDIA` is told the read-only folder that refuses a delete.
- **One owner for who sees an Event.** Only `src/events.rs` decides which subscriber gets an Event and what of it; handlers pass the caller.
- **Spans carry ids, not words.** A span's fields hold only ids (Item, Library, User, Device, Plugin), counts, sizes, durations, codecs and outcomes, never a title, file path, name, IP address or search text, since the Hub forwards them as they are when an admin shares Diagnostics (ADR 0054).
- **Forwarded headers from trusted proxies only.** Read where a request came from (client IP, HTTPS) from the `RequestSource` that `src/forwarded.rs` sets. It believes `X-Forwarded-*` only from a peer in `Config::trusted_proxies` (ADR 0018), since any client can set them.

### Tests

- **One fixture.** Server tests in `tests/` build on `TestServer` in `tests/support`, started through `TestServer::builder()`. Their setup goes through the API, as a client's would; a shared helper never writes the database. A test file adds a fixture of its own only for what that file alone needs, and a shortcut one test needs stays in that test's file.
- **One in-file fixture.** An in-file test that needs a Library with a Matched Movie builds it with `library::fixture` and adds what else it needs on top, so a change to how a Match is stored touches one place.
- **Fake programs.** Fake programs a test runs are written only through `ffmpeg::fake::script`. Writing one with `fs::write` can fail with "Text file busy" (#411).
- **Unit tests sit beside their file, or in their area's folder.** `foo.rs`'s unit tests live in `foo_tests.rs` beside it, which `foo.rs` declares as `#[cfg(test)] #[path = "foo_tests.rs"] mod tests;`. An area root, or a single file with a folder of its own (`browse`, `server_settings`, `plugin_settings`), keeps its unit tests in that folder instead, as `<area>/<area>_tests.rs`, which `<area>.rs` declares as `#[cfg(test)] #[path = "<area>/<area>_tests.rs"] mod tests;`. A single file without a folder (`connections`, `db`, `events`, `forwarded`) keeps its test file beside it. Either way each test keeps its name. `tests/structure.rs` checks it.
- **One clock.** Server code reads the time only through `db::now` or `db::now_ms`, which a Plugin's `nama.now` reads too, so a test moves every clock the Kernel or a Plugin sees with `db::advance_clock` (`testing` feature, process-wide; `TestServer::advance_clock` in `tests/support`). A test that moves it builds its `TestServer` with `moves_clock()`, which runs it alone among its binary's `TestServer`s, since `cargo test` runs a binary's tests in one process. Two exceptions: Diagnostics' span timestamps, in `src/diagnostics.rs`, must match the real time the exporter stamps its other spans with, and a migration that backfills a time reads SQLite's `unixepoch()`, since migrations run in SQL before the Server has a clock.

### Structure

- **File size.** No `.rs` file under `src/` or `tests/`, nor `build.rs`, is over 800 lines, except those `tests/structure.rs` lists with a ceiling, a multiple of 100 lines the file stays at or under. A ceiling only comes down, to the next 100 above the file as it shrinks, and its entry goes once the file is 800 lines or fewer. The table takes a new file only when a move-only change makes it out of a listed one.
- **Owned tables.** Each table a "One owner" rule here or in an area's `AGENTS.md` names is listed with its owner in `tests/structure.rs`, which fails on SQL naming it in any other file, tests included. A new such rule adds its tables there.
- **Named paths exist.** A path an `AGENTS.md` here names in backticks, one with a `/` in it, exists relative to that file's folder or the workspace root. `tests/structure.rs` checks it, so a move updates the rules that name what moved.
- **Rows.** A module calls only a lower row, or a module to its right in its own row, of `ROWS` in `tests/structure.rs`, which fails on any other `crate::` path not in its `ALLOWED_UPWARD`; a new top-level file gets a place there (ADR 0051).
- **Area surfaces.** Neighbours import only what an area's root (`<area>.rs`) re-exports, and items inside an area default to `pub(super)`. A module neighbours reach by path anyway is listed with its reason in `SURFACE_EXCEPTIONS` in `tests/structure/surfaces.rs`, which fails on any other `crate::<area>::<module>::` path from outside the area. An area's `AGENTS.md` is at most 30 lines: its invariants, then its Neighbours.
- **Area rules.** An area's folder holds an `AGENTS.md` with the area's own rules and its neighbours; read it before changing the area. A rule lives once, in the nearest `AGENTS.md`.
