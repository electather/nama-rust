## nama-server

### Data

- **One database writer.** Every write goes through `Database::write` or `Database::write_then` in `src/db.rs`, on the one writable SQLite connection. Long jobs such as a scan write in small batches.
- **One owner for a Library's contents.** Only `src/contents.rs` reads or writes `library_files`, `library_items`, `item_matches`, `match_pins` and `title_search`, tests included. Everything else goes through `Contents`.
- **One owner for Tracks.** Only `src/tracks.rs` reads or writes `version_probes`, `tracks` and `probe_failures`, tests included. Browse attaches them to the Versions `Contents` reads.
- **One owner for probing.** Only Probing (`src/probing.rs`, with its private `src/probing/ffprobe.rs`) runs ffprobe on stored files and decides what a probe failure means for trying it again (`ProbeFailure`); Tracks stores it.
- **One owner for asking the metadata Provider.** Only `src/metadata.rs` (`MetadataSource`) calls a `MetadataProvider` and decides what its failures mean. Matching, Requests, Artwork and handlers ask it and read its `Error`.
- **One owner for Quality rules.** Only `src/qualities.rs` reads or writes `qualities` and `default_qualities`, tests included, and decides which Quality a Request, Show or Followed Show takes (ADR 0025). Requests and handlers ask it.
- **One owner for Server settings.** Only `src/server_settings.rs` reads or writes `server_settings`, tests included.
- **One owner for stored images.** Only `ImageStore` in `src/images.rs` reads or writes the image files in the data directory, tests aside (ADR 0037). Artwork and later image kinds go through it.
- **One owner for Track Preferences.** Only `src/track_preferences.rs` reads or writes `track_preferences`, tests included, and decides what a Preference is kept for: the Show or Movie a Version is of, never an Item or file (ADR 0035).
- **One owner for Watch State.** Only `src/watch_states.rs` reads or writes `watch_states`, tests included, and keys it by a Movie's or Episode's external id, never an Item or file (ADR 0013). Browse works out which Movie or Episodes a Version or a marked title stands for and asks `WatchStates`.
- **One path for Request changes.** Every change to a Request or Followed Show goes through `Requests::apply`, which alone publishes their events and hands off (ADR 0029). A Library's write making them Available is the exception (ADR 0012).
- **One path for Library changes.** Outside tests, creating, updating or deleting a Library goes through `Scanner::create_library`, `update_library` or `delete_library`, which alone do what must follow it (re-watching folders, cleaning a deleted Library's cached subtitles) in a task that outlives the caller (ADR 0029). Handlers read through `Libraries`.
- **One path for deleting media.** Every delete of media files, the API's and later the cleanup Plugin's (#700), goes through `Scanner::delete_media`, which deletes under the Library's scan lock in a task that outlives the caller, ends the Playback Plans playing what goes first, removes the Versions through `Contents` and logs who deleted what (ADR 0038).
- **Requester rules once.** What a Request and a Followed Show share (Requesters, the guarded Pending decision, who may see one) is written once in `src/requests/asked.rs`; each keeps only what differs.
- **One owner for Plugin changes.** Outside tests, only `src/plugin_settings.rs` enables or disables a Plugin or saves its settings, under its one lock and in ADR 0028's order. The type enforces it: only Plugin settings and startup hold the `Registry`, and every other module holds its `ExtensionPoints`, which calls Plugins but can't enable, disable or list them. Handlers and tasks ask `PluginSettings`.
- **Migration list.** A new migration's file name also goes as the last line of `migrations.txt`, so two PRs adding the same migration number conflict in git (#561); a test checks it.
- **Query data.** After changing a `sqlx::query!` or anything in `migrations/`, regenerate `.sqlx/` at the workspace root and commit it (commands in `README.md`).
- **Name parser version.** A change to how names are parsed or how Matching decides that could turn an Unmatched Item into a Match bumps `PARSER_VERSION` in `src/scanner/names.rs`, so the next scan parses stored files again and retries their automatic Unmatched decisions (ADR 0023). So does a change to what Matching stores about an automatic Unmatched decision, such as why it was made, so decisions stored before it get it.
- **Probe version.** A change to what probing reads from a file, or how, bumps `PROBE_VERSION` in `src/tracks.rs`, so the next pass after a scan probes every file again (ADR 0023's pattern).
- **Probe failure version.** A change that may let ffprobe read files it lastingly failed on before, without changing what probing reads from a file that it could read, bumps `PROBE_FAILURE_VERSION` in `src/tracks.rs`, so the next pass tries again only those files.
- **WebVTT version.** A change to the WebVTT a subtitle source makes bumps `WEBVTT_VERSION` in `src/playback/subtitles.rs`, so what the cache kept from before is made again.
- **Whole-Library reads.** Browse reads a Library's whole contents even to find one title. Each such read is marked `// ponytail: whole-Library read`; query by id there once Libraries get big.

### API

- **One part per domain.** An RPC's handler, its proto conversions and the mapping of its module's errors to Refusals go in its domain's part under `src/api/`, such as `libraries.rs` or `sign_in.rs`. `src/api.rs` holds only the router, the access layer (`ACCESS`, the check that reads it, `NEEDS_RECENT_AUTHENTICATION`), `refuse` with the reason table, and helpers more than one part uses. A conversion two parts use lives with the part that owns its type.

### Security

- **Secrets stay out of storage and logs.** The database holds the Authenticator's credential string and the SHA-256 hash of each session token; only `src/users.rs` derives them. Types holding a token or Sign-in Code skip `Debug`. The Setup Code is the one secret logged, on purpose. Plugin settings are the one secret stored as written, since a Plugin must send a key such as TMDB's as it is: no setting value is ever logged (the `Debug` of `SettingValue` and `PluginTables` hides them), and a secret's value, stored or default, is never sent to a client (`setting_to_proto` in `src/api/plugins.rs`).
- **Clients name ids.** Media is served by Version id (`Contents::version_file`) and artwork only for paths some Match stores (`Contents::stores_image`) or a Movie or Show search or lookup handed out (`Artwork::offer`). Where a Library lives on disk is shown only to Users with `MANAGE_LIBRARIES`.
- **One owner for who sees an Event.** Only `src/events.rs` decides which subscriber gets an Event and what of it; handlers pass the caller.
- **New RPCs start closed.** `ACCESS` in `src/api.rs` declares, once per RPC, who may call it: anyone, any signed-in User, or a User whose Permissions pass a check for one Permission (`Permissions::allow` in `src/users.rs`: `ADMIN` passes every check) (ADR 0020). An RPC missing from it is refused to everyone, session or not, with the router's own 404 for an unknown path (no Refusal), and a test fails until it is listed. Media under `/media/` needs a session (`MEDIA`). A self-service RPC (your own Devices or password) is signed-in and its handler checks ownership.
- **Sensitive RPCs need Recent Authentication.** An RPC that changes who can sign in as whom (a password, a Sign-in Method, a User's Permissions or the default ones, deleting a User, approving a Sign-in Code), or that deletes media, goes in `NEEDS_RECENT_AUTHENTICATION` in `src/api.rs` (ADR 0014). The access layer checks it before the handler runs; handlers don't check it themselves.
- **Guessable requests go through `SignIn` (`src/sign_in.rs`).** It lets an attempt through before reading a User or a secret, and un-counts it the moment the secret checks out; a failure after that, or an input check before it, is no guess. Sign-in Codes count only an unknown or expired code.
- **Forwarded headers from trusted proxies only.** Read where a request came from (client IP, HTTPS) from the `RequestSource` that `src/forwarded.rs` sets. It believes `X-Forwarded-*` only from a peer in `Config::trusted_proxies` (ADR 0018), since any client can set them.
- **Causes stay server-side.** A database or server-side error is logged; the client gets a generic Connect error.
- **Refusals are typed.** Every error a client can cause carries a `nama.v1.Refusal` detail (ADR 0019). Build it with `refuse` in `src/api.rs`, which sets the Connect code from the `RefusalReason` and fills `debug`; never build a client-caused `ConnectError` directly. The one exception is the router's 404 for a path no `ACCESS` entry lists (see "New RPCs start closed"). A refusal about one request field names it in `field`, and values its message mentions go in `params` (AIP-193: lowerCamelCase keys, units in the key). Server-side failures carry none.
- **Plugin code runs contained.** Every call into a Plugin, its `Drop` included, goes through `contain_sync` (or its async twin) in `src/plugins.rs`, outside the registry lock. A Provider's error is Plugin code too: the Registry formats it into a `Failure`, blanks the Plugin's secret settings in it and drops it, all inside containment, so a caller gets only the `Failure` and never formats or drops a Plugin's error itself. A caller that branches on the kind of failure maps the error to a Kernel-side kind with `ProviderError`. The one exception is an Authenticator hashing or checking a password on a blocking thread (`blocking` in `src/users.rs`): a panic there fails that call and leaves the Plugin enabled, since disabling the only Authenticator on a password anyone can choose would lock every User out.

### Playback

- **What a plan converts is worked out once.** Before the steps run, `candidates` in `src/playback.rs` works out what a Remux and a Transcode of the Version would convert, and the plan keeps the one it narrowed to in `Playing`, with the Version's length, which a Remux's or a Transcode's playlist lists, and, for a Transcode on hardware, what it falls back to in software and why. Its reasons, Tracks, events, playlist and ffmpeg arguments read that value; none asks the planning facts again what it converts, how long the Version is or what it falls back to.
- **What ffmpeg can do is asked once.** Only `Abilities` in `src/ffmpeg.rs` asks the Server's ffmpeg whether it runs, has zscale or libx264, and which hardware passes its test on which GPU, and remembers each answer; whether it has zscale or libx264, and which hardware passes when it couldn't list its encoders, is asked again while ffmpeg couldn't say. Planning and the `GetPlaybackStatus` and `UpdatePlaybackSettings` handlers read the one `CanDo` it hands back, and ask its methods what follows: whether a Transcode runs, what tone-maps HDR on each hardware, and which Automatic picks. `RunningPlans` knows only running plans.

### Tests

- **One fixture.** Server tests in `tests/` build on `TestServer` in `tests/support`, started through `TestServer::builder()`. Their setup goes through the API, as a client's would; a shared helper never writes the database. A test file adds a fixture of its own only for what that file alone needs, and a shortcut one test needs stays in that test's file.
- **One in-file fixture.** An in-file test that needs a Library with a Matched Movie builds it with `contents::fixture` and adds what else it needs on top, so a change to how a Match is stored touches one place.
- **Fake programs.** Fake programs a test runs are written only through `ffmpeg::fake::script`. Writing one with `fs::write` can fail with "Text file busy" (#411).
