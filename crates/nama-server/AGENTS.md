## nama-server

### Data

- **One database writer.** Every write goes through `Database::write` or `Database::write_then` in `src/db.rs`, on the one writable SQLite connection. Long jobs such as a scan write in small batches.
- **One owner for Server settings.** Only `src/server_settings.rs` reads or writes `server_settings`, tests included.
- **One owner for Plugin changes.** Outside tests, only `src/plugin_settings.rs` enables or disables a Plugin or saves its settings, under its one lock and in ADR 0028's order. The type enforces it: only Plugin settings and startup hold the `Registry`, and every other module holds its `ExtensionPoints`, which calls Plugins but can't enable, disable or list them. Handlers and tasks ask `PluginSettings`.
- **Migrations name nothing shared.** The table files `0001` to `0036` are frozen. No test, file or check names, lists or counts the migrations after them, since each would make every migration PR edit it and conflict (ADR 0059). An upgrade test that runs the migrations before its own and checks what its own does to existing data names only its own version. A new migration is named by its UTC creation time, assumes only what was on main when its PR opened, and is never renamed once pushed; `tests/server/db.rs` checks the name.
- **Upgrades are one transaction, forward only (ADR 0060).** `Database::open` runs every pending migration in one transaction with foreign keys off, and rolls it all back if `PRAGMA foreign_key_check` finds a broken key, so a rebuild may drop a table others reference. No migration is `-- no-transaction`. A rebuild recreates the table's indexes and triggers, since `DROP TABLE` takes them along, and its PR shows the table's `sqlite_schema` rows before and after. A migration on main is never edited, renamed or deleted: add a new one (`.github/scripts/migrations-unchanged.sh` checks it).
- **Query data.** After changing a `sqlx::query!` or anything in `migrations/`, regenerate `.sqlx/` at the workspace root and commit it (commands in `README.md`).
- **Config schema.** A change to `Config` regenerates `docs/nama.schema.json`, which editors check `nama.toml` against: `tests/server/config.rs` rewrites it and fails until it's committed.
- **One owner for what a Plugin leaves behind.** `LEFTOVERS` in `src/plugin_settings/leftovers.rs` lists every table keyed by a Plugin with when its rows go, or why they stay, and that module's three calls delete them through each table's owner. A new table naming a Plugin goes on that list; its test reads the schema and fails until it does.
- **Per-title data keys on External ID.** Every store of a title's data, or a User's data about a title, keys on the title's External ID, never on an Item, a Version or a file, so it outlives a rename, a new Version, a rescan or a remount (ADR 0013, ADR 0042): Custom Images, Watch State, Subtitle and Audio Preferences, Requests, Followed Shows, hiding from Continue Watching, the Watchlist (ADR 0056), and to come collections, playlists and ratings. Pinned Matches are the exception: they key on the parsed name, since a Pinned Match says which title that name is, whichever file bears it. Downloaded subtitles, Segments, Preview frames and Subtitle Offsets are the others: they key on the Version, since their timing and a frame fit one file (ADR 0067, ADR 0074, ADR 0076, ADR 0070).
- **One owner for the Watchlist.** Only `src/watchlist.rs` reads or writes `watchlist`, tests included. A title is on a User's Watchlist when it's there under any of its ids. A title taken off stays as a removal (`removed`), with when each change was made, so the Hub syncs the change made last (ADR 0056): every read but sync's leaves removals out.
- **One owner for when sync runs.** Only `src/sync.rs` (`Syncing`) decides when a Linked User's Watch State, Track Preferences and Watchlist move between the Server and the Hub (ADR 0008, ADR 0056, ADR 0092, ADR 0105): which of push, pull and Watchlist sync each trigger runs (the table at its top), that a push comes before its pull, when what waits for the Hub is sent, and doing no sync work when the Server's config names no Hub. A handler makes one call naming what happened, and each returns at once. Startup starts its Scan follower before the scans, so it sees their Matching finish, and its Link follower before serving, so it hears the first look at each Link. It reaches the Hub only through `Linking`.
- **One owner for Linking.** Only `src/link.rs` (`Linking`) calls the Kernel's Link with the Hub its config names (ADR 0105): the Server's own, which only `src/link/server.rs` keeps, in `hub_link`, `hub_key_set` and `hub_tokens_used`, and its Users' Links and signing in with an Account, which only `src/link/users.rs` keeps, in `hub_user_links`. What a Linked User's Watch State and Track Preference changes and Viewing Events wait in for the Hub, `hub_sync_queue`, only `src/link/sync.rs` reads and writes, and each owner queues its changes there in the write that makes them, as `src/viewing.rs` does each play once it ends; what the Hub accepts is named once, in `src/link/hub.rs`. What the Hub suggests, which Plugins ask through the Kernel's `list_hub_*` functions, it asks in `src/link/suggestions.rs`. `Linking` names each call's bound once (the table at its top), answers in the Kernel's terms, and tells its followers when a look finds a Link newly Linked, and, apart, each time the Server keeps or forgets a Link, which `src/events.rs` announces to Plugins. A Server whose config names no Hub never calls one (ADR 0002). Whether a User still has a way in, their Account among them, is Users' to answer (`src/users/accounts.rs`).
- **Whole-Library reads.** Browse reads a Library's whole contents even to find one title. Each such read is marked `// ponytail: whole-Library read`; query by id there once Libraries get big.

### Security

- **Secrets stay out of storage and logs.** The database holds the Authenticator's credential string, the argon2id hash of each Switch PIN and the SHA-256 hash of each session token; only `src/users/passwords.rs` derives the credential and the Switch PIN's hash, and `src/users.rs` the token's hash. Types holding a token or Sign-in Code skip `Debug`. The Setup Code is the one secret logged, on purpose. Four secrets are stored as written, since each is used as it is: the Server's Hub credential in `hub_link`, which no `Debug` shows, its VAPID key in `server_settings` and each browser's push subscription in `push_subscriptions`, which `VapidKey` and `Subscription` have no `Debug` to show and no log names, and Plugin settings, such as TMDB's key: no setting value is ever logged (the `Debug` of `SettingValue` and `PluginTables` hides them), and a secret's value, stored or default, is never sent to a client (`setting_to_proto` in `src/api/plugins.rs`).
- **Clients name ids.** Media is served by Version id (`Contents::version_file`), an image beside the media only as a copy some Version's row records (`Contents::local_image_type`), and artwork only for paths some Match stores (`Contents::stores_image`) or a Movie or Show search, lookup, a Home row's or Box Set's missing title, a Box Set's Poster or Backdrop, or a title's or Season's artwork list handed out (`Artwork::offer`), and a Custom Image is picked only from those, downloaded through its title source (`Artwork::offered_bytes`), into whatever Custom Image slot the admin names: an upload can put any bytes there anyway, so offers aren't bound to slots. Where a Library lives on disk is shown only to Users with `MANAGE_LIBRARIES`, except that a User with `DELETE_MEDIA` is told the read-only folder that refuses a delete.
- **One owner for who sees an Event.** Only `src/events.rs` decides which subscriber gets an Event and what of it; handlers pass the caller.
- **Spans carry ids, not words.** A span's fields hold only ids (Item, Library, User, Device, Plugin), counts, sizes, durations, codecs and outcomes, never a title, file path, name, IP address or search text, since the Hub forwards them as they are when an admin shares Diagnostics (ADR 0054).
- **Shared lines are marked where they're logged.** A log line reaches the Hub only once its call site has `shared = true` and a `name:`, and a Usage Analytics event only as a `Usage` variant in `src/diagnostics.rs`. A shared line, its message included, holds only what a span may, so review every `shared = true` a diff adds (ADR 0054).
- **A span whose work fails says so.** Mark it with `diagnostics::outcome`, `failed_with` or `failed`, whose `error.type` is a type name or a constant kind, never a message. An outcome that isn't trouble, such as a cancelled scan or a Plugin's "not found", stays unmarked.
- **Setup and load go in the `server status` span** (`src/status.rs`), as counts rounded to a power of ten and sizes, never names or paths.
- **CORS for the Hub only.** Only `src/api/hub_cors.rs` approves a call from another origin: the origin of the Hub its config names, while the Server is Linked, never with credentials nor for a request carrying a cookie (ADR 0015, ADR 0105).
- **Bearer callers get signed media URLs (ADR 0105).** An `<img>`, `<video>` or `<track>` can't send a bearer token, so every media URL a response gives is signed for a bearer caller, through `ImageSources::shown` or `url_signer` in `src/api.rs`, and a cookie caller's stays as it is. An image's covers its one path; a playback URL's covers its Version and plan and acts as the User and Device it was planned for (`Viewer`), so a media route a playback URL reaches reads who asks with `viewer_of` in `src/playback/direct_play.rs`, never the `Caller` alone. A new media URL in a response is signed the same way, or a bearer caller can't load it. The one exception is a download's under `/media/downloads/`, which a native client fetches with its token: a signed one would skip the `DOWNLOAD` check.
- **Forwarded headers from trusted proxies only.** Read where a request came from (client IP, HTTPS) from the `RequestSource` that `nama-forwarded`, shared with the Hub, sets. It believes `X-Forwarded-*` only from a peer in `Config::trusted_proxies` (ADR 0018), since any client can set them.

### Tests

- **One fixture.** Server tests in `tests/` build on `TestServer` in `tests/support`, started through `TestServer::builder()`. Their setup goes through the API, as a client's would; a shared helper never writes the database. A test file adds a fixture of its own only for what that file alone needs, and a shortcut one test needs stays in that test's file.
- **A new integration test is a module of `tests/server/`**, never a top-level file in `tests/`: each top-level test file links the Kernel and wasmtime again. `tests/structure.rs` fails on one it doesn't list.
- **One in-file fixture.** An in-file test that needs a Library with a Matched Movie builds it with `library::fixture` and adds what else it needs on top, so a change to how a Match is stored touches one place. One that needs a title source or a Similar source scripts a `ScriptedSource` from `library::scripted` and enables it as its own Plugin, so a change to what a title source is asked touches one place; a test needing what it can't script writes its own, with a line saying why. One that needs a Fulfiller scripts a `plugins::ScriptedFulfiller` the same way.
- **Fake programs.** Fake programs a test runs are written only through `ffmpeg::fake::script`. Writing one with `fs::write` can fail with "Text file busy" (#411).
- **Unit tests sit beside their file, or in their file's folder.** `foo.rs`'s unit tests live in `foo_tests.rs` beside it, which `foo.rs` declares as `#[cfg(test)] #[path = "foo_tests.rs"] mod tests;`. An area root, or a file at any depth with a folder of its own (`browse`, `server_settings`, `plugin_settings`, or a nested one such as `src/playback/choices.rs`), keeps its unit tests in that folder instead, as `<name>/<name>_tests.rs`, which `<name>.rs` declares as `#[cfg(test)] #[path = "<name>/<name>_tests.rs"] mod tests;`. A single file without a folder (`connections`, `db`) keeps its test file beside it. Either way each test keeps its name. `tests/structure.rs` checks it.
- **One log capture.** A unit test that reads what the Server logs captures it with `CapturedLog` in `src/log_capture.rs`, never with a thread-local subscriber of its own, which misses lines another test's thread reached first under `cargo test` (#945). No unit test sets a global subscriber: `CapturedLog` owns the process's one.
- **One clock.** Server code reads the time only through `db::now` or `db::now_ms`, which a Plugin's `nama.now` reads too, or, to time how long ago something happened, the monotonic `db::instant_now`, so a test moves every clock the Kernel or a Plugin sees with `db::advance_clock` (`testing` feature, process-wide; `TestServer::advance_clock` in `tests/support`). A test that moves it builds its `TestServer` with `moves_clock()`, which runs it alone among its program's `TestServer`s should they share a process, and starts it on the real clock with `db::reset_clock`, so an earlier test's moves don't add up with its own. Integration tests run under nextest, which keeps them apart, each in its own process. `restart` keeps the clock the test moved. Lib tests share the offset with nothing isolating them, so they step it by seconds only. Two exceptions: Diagnostics' span timestamps, in `src/diagnostics.rs`, must match the real time the exporter stamps its other spans with, and a migration that backfills a time reads SQLite's `unixepoch()`, since migrations run in SQL before the Server has a clock.

### Structure

- **File size.** No `.rs` file under `src/` or `tests/`, nor `build.rs`, is over 800 lines, except those `tests/structure.rs` lists with a ceiling, a multiple of 100 lines the file stays at or under. A ceiling only comes down, to the next 100 above the file as it shrinks, and its entry goes once the file is 800 lines or fewer. The table takes a new file only when a move-only change makes it out of a listed one.
- **Owned tables.** Each table a "One owner" rule here or in an area's `AGENTS.md` names is listed with its owner in `tests/structure.rs`, which fails on SQL naming it in any other file, tests included. A new such rule adds its tables there.
- **Named paths exist.** A path an `AGENTS.md` here names in backticks, one with a `/` in it, exists relative to that file's folder or the workspace root. `tests/structure.rs` checks it, so a move updates the rules that name what moved.
- **Rows.** A module calls only a lower row, or a module to its right in its own row, of `ROWS` in `tests/structure.rs`, which fails on any other `crate::` path not in its `ALLOWED_UPWARD`; a new top-level file gets a place there (ADR 0051).
- **Area surfaces.** Neighbours import only what an area's root (`<area>.rs`) re-exports, and items inside an area default to `pub(super)`. A module neighbours reach by path anyway is listed with its reason in `SURFACE_EXCEPTIONS` in `tests/structure.rs`, which fails on any other `crate::<area>::<module>::` path from outside the area; `crate::<area>::<module>` alone is no reach when the root re-exports an item under the module's name (`pub use <module>::<module>;`). An area's `AGENTS.md` is at most 30 lines: its invariants, then its Neighbours.
- **Area rules.** An area's folder holds an `AGENTS.md` with the area's own rules and its neighbours; read it before changing the area. A rule lives once, in the nearest `AGENTS.md`.
