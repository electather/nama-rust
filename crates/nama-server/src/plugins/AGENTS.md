## Plugins

The Registry, how the Kernel calls Plugins at Extension Points, and the Built-in and Installed Plugins (ADR 0006).

- **Plugin code runs contained.** Every call into a Plugin, its `Drop` included, goes through `contain_sync` (or its async twin) in `plugins.rs`, outside the registry lock. Each such call also runs in the span `ExtensionPoints::log_span` gives, which names a Built-in on each line it logs with `tracing` (ADR 0061); only what runs before the Server knows its id (making a Plugin to describe it, asking its Manifest, and dropping one whose Manifest panicked) runs outside it. A Provider's or Observer's error is Plugin code too: the Registry formats it into a `Failure`, blanks the Plugin's secret settings in it and drops it, all inside containment, so a caller gets only the `Failure` and never formats or drops a Plugin's error itself. A caller that branches on the kind of failure maps the error to a Kernel-side kind with `ProviderError`. The one exception is an Authenticator hashing or checking a password on a blocking thread (`blocking` in `users.rs`): a panic there fails that call and leaves the Plugin enabled, since disabling the only Authenticator on a password anyone can choose would lock every User out.
- **Asking records the answer for the Plugins page.** `ExtensionPoints::ask`, `ask_one` and `ask_first` record each call: a failure whose kind `FailureKind` counts, or else an answer, so no caller records by hand. A read of what a Provider says of itself, such as which methods it serves, goes through `read_provider`, which records nothing, since that answer would clear a real failure. A Fulfiller's `needs` check (`unmet` in `fulfilling.rs`), read inside the ask, is a marked `ponytail:` ceiling.
- **A Kernel task that calls one Plugin repeatedly runs in its scope.** Start it with `ExtensionPoints::spawn_in`, so disabling, re-enabling or shutdown cancels and joins it before the Plugin is dropped (ADR 0047). `Registry::disable` waits for that join, so a caller inside the Plugin's own call or scope uses `disable_now`.
- **A Fulfiller is asked about a title only through `fulfilling.rs`.** `enabled_fulfiller` names a kind's one Fulfiller; `ask_fulfiller` runs the needs check and the call in containment and returns a `FulfillerOutcome`; `tell_fulfiller`, for a caller that only logs, asks again on try-again in the Plugin's scope, stops after `RETRIES` and hands the caller's log why, once. The Hand-off's retry is `requests`' own, since it reads the Request again and fails it.
- **A scope's cancel fires its enablement's `Stop`** (`nama_plugin_api::Stop`, in containment, before the join): an Installed Plugin's running WASM calls are interrupted, not counted as crashes, and the old `EnabledKernel` refuses from then on (ADR 0047).
- **A Job fires on its cron, in its Plugin's scope** (`jobs.rs`, ADR 0079): one loop per scheduled Job, once the Kernel serves, since the Kernel refuses every call before then, reading the Kernel's clock in the Server's time zone. Each Run, the loop's or an Admin's (`run_now`), claims its Job in `RunningJobs` for as long as it runs, so a firing due meanwhile is dropped and a Run now refused; the loop counts from its own start, so missed firings aren't made up. One `jobs::refusal` refuses a Built-in's Jobs at enable and an Installed Plugin's at load (`wasm/load.rs`). Each Run's `job_runs` row is written as it starts and closed as it ends, the last 50 per Job kept; a Run the scope's cancel drops is closed `interrupted` by its `Recording`'s drop, a write `Registry::shutdown` waits for, and startup closes any left running (`Registry::record_job_runs_in`). An Admin's change to a Job, turning it off or giving it a schedule of its own, is a `job_overrides` row only while it differs from the Manifest (`job_overrides.rs`); the loop reads it each minute, so it applies without a restart. Startup and listing the Plugins delete the overrides and Runs of Jobs no Plugin declares, except a refused Plugin's.
- **The Kernel can't tell a Built-in from an Installed Plugin.** An Installed Plugin runs through Extism behind the same `Plugin` trait (`wasm.rs`); only listing, saving a crash and `log_span` tell the two kinds apart.
- **Extism stays in `wasm`.** `wasm.rs` and `wasm/` hold everything Extism.
- **The Kernel's functions are imports that pass along.** Each `nama` import an Installed Plugin calls is a name in the contract's table of Kernel functions (`crates/nama-plugin-proto/AGENTS.md`); `wasm/automation.rs` hands its name and bytes to the enablement's `Kernel::call` and wraps what it answers in a `KernelAnswer`. Decoding, the Permission and the work are the `automation` area's. `nama.now` and `nama.log` answer no Kernel function, so they are imports of their own.
- **Each method has its own time limit.** Its row in `wasm/services.rs` carries it (`CALL_TIMEOUT`, `JOB_TIMEOUT` for a Job's Run, `BLOB_TIMEOUT` for a blob store call, or `HOME_ROWS_TIMEOUT` for a Home row refresh), and the watchdog in `wasm/calls.rs` counts only the Plugin's own time against it: a `nama` import pauses the call's clock while the Kernel answers, except `nama.log` (`wasm/plugin_log.rs`), so a Plugin logging in a loop still meets its limit. A call that ends at its limit interrupts every call on its compile; those fail as `Collateral`, which isn't a crash. So a point with any row past `CALL_TIMEOUT` (`Point::runs_long`: the Job runner, the blob store and the Home row source) gets a compile of its own, and a test must not assume only a Job's Run runs long.
- **What the Kernel gives an Installed Plugin is contract.** The limits on a call, the `nama` functions and how settings and HTTP reach it (`wasm/load.rs`) follow `crates/nama-plugin-proto/AGENTS.md`.

### Neighbours

- Uses: `images` (cleaning a Manifest's logo).
- Uses: `images` (`Blobs`, which `PluginBlobs` in `blob_store.rs` serves from a blob store Plugin).
- Uses: `diagnostics` (marking a Plugin call's span failed, keeping a spawned call in its caller's trace, starting and forgetting a Plugin's kept Plugin Log lines as it is enabled and disabled, and the span that gives a Job Run's lines its id).
- Used by: `plugin_settings` (the `Registry`), startup in `main.rs`, and, through `ExtensionPoints`, `library` (`TitleSources`, `Recognisers`, `Artwork`, `SimilarSources`), `matching`, `scanner`, `requests`, `home_rows`, `events`, `connections`, `users` and the `api` part for Plugins, which reads Job Runs with `job_runs` and starts one with `run_now`, changes a Job with `configure_job` and `preview_schedule`.
