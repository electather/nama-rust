## Plugins

The Registry, how the Kernel calls Plugins at Extension Points, and the Built-in and Installed Plugins (ADR 0006).

- **Plugin code runs contained.** Every call into a Plugin, its `Drop` included, goes through `contain_sync` (or its async twin) in `plugins.rs`, outside the registry lock. Each such call also runs in the span `ExtensionPoints::log_span` gives, which names a Built-in on each line it logs with `tracing` (ADR 0061); only what runs before the Server knows its id (making a Plugin to describe it, asking its Manifest, and dropping one whose Manifest panicked) runs outside it. A Provider's error is Plugin code too: the Registry formats it into a `Failure`, blanks the Plugin's secret settings in it and drops it, all inside containment, so a caller gets only the `Failure` and never formats or drops a Plugin's error itself. A caller that branches on the kind of failure maps the error to a Kernel-side kind with `ProviderError`. The one exception is an Authenticator hashing or checking a password on a blocking thread (`blocking` in `users.rs`): a panic there fails that call and leaves the Plugin enabled, since disabling the only Authenticator on a password anyone can choose would lock every User out.
- **Asking records the answer for the Plugins page.** `ExtensionPoints::ask`, `ask_one` and `ask_first` record each call: a failure whose kind `FailureKind` counts, or else an answer, so no caller records by hand. A read of what a Provider says of itself, such as which methods it serves, goes through `read_provider`, which records nothing, since that answer would clear a real failure. A Fulfiller's `needs` check (`requests::unmet`), read inside the ask, is a marked `ponytail:` ceiling.
- **A Kernel task that calls one Plugin repeatedly runs in its scope.** Start it with `ExtensionPoints::spawn_in`, so disabling, re-enabling or shutdown cancels and joins it before the Plugin is dropped (ADR 0047). `Registry::disable` waits for that join, so a caller inside the Plugin's own call or scope uses `disable_now`.
- **A scope's cancel fires its enablement's `Stop`** (`nama_plugin_api::Stop`, in containment, before the join): an Installed Plugin's running WASM calls are interrupted, not counted as crashes, and the old `EnabledKernel` refuses from then on (ADR 0047).
- **An Automation ticks once the Kernel serves, then every `tick_every`** (`tick.rs`), in its Plugin's scope: at enable, so an Admin sees it act at once, or for a Plugin enabled at startup once serving starts, since the Kernel refuses every call before then. Disabling ends the loop, waiting or not.
- **A test ticks an Automation now** with `Registry::tick_now` (`testing` feature), which runs the schedule's own `tick::once`. A test whose ticks mustn't race a scheduled one calls `Registry::tick_only_on_demand` before enabling its Plugins, so they never tick on their own (#986).
- **The Kernel can't tell a Built-in from an Installed Plugin.** An Installed Plugin runs through Extism behind the same `Plugin` trait (`wasm.rs`); only listing, saving a crash and `log_span` tell the two kinds apart.
- **Extism stays in `wasm`.** `wasm.rs` and `wasm/` hold everything Extism.
- **Each method has its own time limit.** Its row in `wasm/services.rs` carries it (`CALL_TIMEOUT`, `TICK_TIMEOUT` for a tick, or `BLOB_TIMEOUT` for a blob store call), and the watchdog in `wasm/calls.rs` counts only the Plugin's own time against it: a `nama` import pauses the call's clock while the Kernel answers, except `nama.log` (`wasm/plugin_log.rs`), so a Plugin logging in a loop still meets its limit. A call that ends at its limit interrupts every call on its compile; those fail as `Collateral`, which isn't a crash. So a point with any row past `CALL_TIMEOUT` (`Point::runs_long`: the Automation and the blob store) gets a compile of its own, and a test must not assume only a tick runs long.
- **The Kernel's functions are table rows.** Each `nama` import an Installed Plugin calls is one row of `FUNCTIONS` in `wasm/automation.rs`, which only decodes, calls `nama_plugin_api::automation::Kernel` and encodes. `nama.now` and `nama.log` answer no `Kernel` call, so they are imports of their own, beside the rows in `build` in `wasm/load.rs`. Whether the Plugin may call it, its Permission check, is the `automation` area's, not this one's.
- **What the Kernel gives an Installed Plugin is contract.** The limits on a call, the `nama` functions and how settings and HTTP reach it (`wasm/load.rs`) follow `crates/nama-plugin-proto/AGENTS.md`.

### Neighbours

- Uses: `images` (cleaning a Manifest's logo).
- Uses: `images` (`Blobs`, which `PluginBlobs` in `blob_store.rs` serves from a blob store Plugin).
- Uses: `diagnostics` (marking a Plugin call's span failed, keeping a spawned call in its caller's trace, and starting and forgetting a Plugin's kept Plugin Log lines as it is enabled and disabled).
- Used by: `plugin_settings` (the `Registry`), startup in `main.rs`, and, through `ExtensionPoints`, `library` (`TitleSources`, `Artwork`), `matching`, `scanner`, `requests`, `events`, `connections`, `users` and the `api` part for Plugins.
