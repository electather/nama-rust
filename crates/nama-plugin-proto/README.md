# nama-plugin-proto

Rust types for the Plugin contract, generated from [`proto/nama/plugin/`](../../proto/nama/plugin) (ADR 0041). `nama.plugin.v1` is the module `nama_plugin_proto::nama::plugin::v1`, holding the messages the Kernel and its Installed Plugins exchange, such as the `Manifest`. `nama-pdk` re-exports this crate, so a Plugin depends on `nama-pdk` alone.

`CONTRACT_VERSION` is the Plugin contract's version, which an Installed Plugin's `Manifest.contract` requirement is matched against. It has a number of its own, separate from this crate's version in `Cargo.toml`; `AGENTS.md` says when it changes.

The contract is more than the messages: `CONTRACT_VERSION` also covers what the Kernel gives an Installed Plugin at run time, below.

Each Extension Point an Installed Plugin can serve is a service of the contract, such as `nama.plugin.v1.NotifierService`, whose rpcs name the exports the Kernel calls (ADR 0043). Each has a version of its own, in `SERVICES`; the `services` module holds their full names. A Manifest names the points it serves in `points`, each by its service's full name and a semver requirement on its version.

`nama.plugin.v1.TitleSourceService`, in [`title_source.proto`](../../proto/nama/plugin/v1/title_source.proto), is a title source the Kernel searches and fetches Movies and Shows from to Match a Library's files. Every one of its exports (`title_search`, `title_movie`, `title_show`, `title_season`, `title_episode`, `title_image`, `title_artwork` and `title_season_artwork`) is optional: the Kernel asks a source only for the ones it has. Its Manifest names in `title_namespace` the id namespace it keeps titles under, such as `tvdb`, and in `title_lookup_namespaces` any others it can look a title up by, such as `imdb`; the Kernel refuses one naming the service without a well-formed namespace in the first, or with a malformed one in the second. Asked by an id in a namespace it can't use, a source answers with `unsupported_id` set, and the Kernel asks the next source. When it stores a Match, the Kernel asks every source in the Library's order that has `title_artwork` for its artwork list and picks the Poster, Backdrop and Title Logo per kind (ADR 0045).

`nama.plugin.v1.RecogniserService`, in [`recogniser.proto`](../../proto/nama/plugin/v1/recogniser.proto), is a Recogniser: it proposes what a file is or which title an Item names, and the Kernel decides (ADR [0050](../../docs/adr/0050-recognisers-propose-what-a-file-is.md)). Both of its exports are optional, and the Kernel asks a Recogniser only for the ones it has. `recognise_title` is asked about an Item the title sources' search couldn't settle, with its name, its files and the candidates the search found, and answers the title's ids; the Kernel takes them only in a namespace one of the Library's title sources serves, and fetches the title as it would for an ID Hint. `recognise_file` is asked about a file the Kernel's name parser made no Item from, such as an Episode numbered from the start of its Show, and answers a Movie or a Show's Season and Episodes, which the Kernel then Matches as usual. An empty answer means the Recogniser can't tell, and the Kernel asks the next one in the Library's order; a failed export leaves the Item or file undecided until the next Scan. The Kernel owns every Match and the Unmatched decision.

`nama.plugin.v1.BlobStoreService`, in [`blob_store.proto`](../../proto/nama/plugin/v1/blob_store.proto), is a blob store: it keeps the Kernel's own stored files, such as the image store's originals, Custom Images and Plugin logos, and never media files (ADR [0052](../../docs/adr/0052-the-kernels-stored-files-live-in-a-blob-store.md)). All five of its exports are required: `blob_put` stores an object at a key, replacing any there; `blob_get` answers it, with `found` false for a missing key rather than a failure; `blob_delete` deletes it, and succeeds for a missing key; `blob_list` answers a page of at most 1000 keys starting with a prefix, with an empty `next_page_token` on the last; and `blob_exists` says whether an object is at a key. A key is `/`-separated, at most 1024 bytes, of ASCII letters, digits and `-_.%/`. One call carries one object of at most `BLOB_MAX_BYTES`, 20 MiB: the Kernel never puts a larger one, and a Plugin may refuse one. A failed export fails the Kernel's read or write.

`nama.plugin.v1.HomeRowService`, in [`home_row.proto`](../../proto/nama/plugin/v1/home_row.proto), is a Home row source: it gives headed rows of titles for the home page, as data the Server draws (ADR [0058](../../docs/adr/0058-plugins-add-to-the-ui-only-as-data-nama-renders.md)). Each of its exports is optional, and serving one is the Plugin's declaration: `shared_rows` answers the rows every User sees, and `user_rows` one User's own, such as their watchlist on an outside service, asked with that User's id and Personal settings and never another's. Each answers rows of a stable key, a heading, a time to live and its titles by kind and id. The Kernel asks ahead of time, never while home loads, in two scopes: the shared rows when the Plugin is enabled or its settings change, and each scope when a User it is for opens home once the first of its rows' time to live, clamped to between 15 minutes and 1 week, has passed, or, for a User's own, once they changed their Personal settings or, for a Plugin granted `PERMISSION_READ_WATCH_STATES`, started a title or marked one played or unplayed. A Plugin without `user_rows` is never asked per User. It keeps the first 3 rows of each answer, the first 200 titles of each and 40 characters of each heading, drops a row whose key repeats, and shows only the titles on the Server; a User's own rows come after the Plugin's shared ones, less one whose key a shared row has. A refresh replaces the Plugin's rows in its scope; one that fails keeps them and is tried again no sooner than 15 minutes on. A User's rows are deleted with the User. Once the Plugin is disabled home shows none of them and the next listing deletes them. The optional `user_featured` export suggests titles for one User's Featured, the top of their home page (ADR [0072](../../docs/adr/0072-featured-is-picked-by-weight-from-kernel-and-plugin-suggestions.md)), asked and kept as `user_rows` is, with a time to live of its own: the Kernel keeps the first 20 suggestions, clamps each weight to between 0.0 and 1.0, and drops a title no Library has. Featured shows the 5 heaviest of the Kernel's suggestions, which weigh at most 0.8, and every Plugin's, a title suggested twice at its heaviest weight.

`nama.plugin.v1.SubtitleSourceService`, in [`subtitle_source.proto`](../../proto/nama/plugin/v1/subtitle_source.proto), is a subtitle source: it searches an outside service, such as OpenSubtitles.com, for a Version's subtitles and downloads one a User picks (ADR [0067](../../docs/adr/0067-subtitles-come-from-a-plugins-source-and-live-in-the-blob-store.md)). Both of its exports are required. `subtitle_search` is asked about one Version, by its Movie's or Show's ids (with the Season and Episode for an Episode), its file name, its OpenSubtitles hash when the Kernel could read it and the languages wanted, and answers results best first, each an id, a language, a name and whether it's SDH. `subtitle_download` is asked for one result's id and answers the file's bytes, at most `BLOB_MAX_BYTES`, and its format by extension, such as `srt`. The Plugin keeps to its service's rate limits; the Kernel neither limits nor counts calls.

`nama.plugin.v1.SegmentSourceService`, in [`segment_source.proto`](../../proto/nama/plugin/v1/segment_source.proto), is a Segment source: it says where a Version's Intro, Recap and Credits are, such as from an outside service like TheIntroDB (ADR [0075](../../docs/adr/0075-each-library-asks-its-segment-sources-after-the-chapter-names.md)). Its one export, `segment_search`, is required. It is asked about one Version, by its Movie's or Show's ids (with the Season and Episode for an Episode) and its duration in milliseconds, and answers Segments, each a kind, a start and an optional end; an empty answer means it doesn't know. The Kernel asks in the background after probing, only the Segment sources a Library lists, in its order, and only for the kinds the Version's Chapter names and earlier sources left unknown; the first answer for a kind wins. It keeps one Segment of each kind, drops one that ends before it starts or starts past the Version's end and cuts an end past it back to it. It asks a Version still missing a kind again at most every 30 days, and one a source failed for an hour later. The Plugin keeps to its service's rate limits.

`nama.plugin.v1.SimilarSourceService`, in [`similar_source.proto`](../../proto/nama/plugin/v1/similar_source.proto), is a Similar source: it says which titles are like a title, the same for every User (ADR 0084). Its one export, `similar_titles`, is required. It is asked about one Movie or Show, by its kind and ids, never with the User, and answers titles of that kind, each by one id with a weight; an empty answer means it knows none and isn't a failure. The Kernel asks every enabled Similar source when it refreshes a title's Matches, and stores each answer per title, replacing that source's last: a failed call keeps it, and an Admin disabling the Plugin deletes its answers, and a page leaves out a disabled Plugin's however it was disabled. Enabling one asks nothing until each title's next refresh. It keeps the 100 heaviest titles of an answer, drops a malformed id and clamps each weight to between 0.0 and 1.0. A page merges the stored answers: a title two sources answer, by any id they share, keeps its heaviest weight, a tie going to the lower Plugin id, and shows the first 20 in a Library, heaviest first. A page for a title not on the Server asks each source live instead, leaving out one that fails.

`nama.plugin.v1.NotifierService`, in [`notifier.proto`](../../proto/nama/plugin/v1/notifier.proto), delivers notifications about Requests. A `Delivery` goes to the Plugin's own channel, to one User's Plugin Connection, or, for a Plugin whose Manifest declares `personal_settings`, to a `UserRecipient`: a User who set the Plugin's Personal settings, with their values, such as their own webhook or topic.

## Personal settings

A Manifest's `settings` are Plugin-wide: an admin sets them once. Its `personal_settings` (ADR 0046) are settings each User sets for themself. Only the TEXT, SECRET, BOOL and INTEGER kinds are allowed, since a User's value must not widen the hosts a Plugin reaches, and a User can't pick from the Admin's Library list: the Kernel refuses a Plugin with a URL, CHOICE or LIBRARIES Personal setting, or with a key that repeats or that `settings` also names. A Plugin never finds them in its Extism config; the Kernel hands one User's values, as text, only in a call for that User, such as a `Delivery` to `UserRecipient`, `user_rows` for that User's Home rows, or `check_personal_settings()` when that User saves them.

## The Job lane

A Plugin's Manifest declares Jobs in `jobs`, each an id, a name, a description and an optional `schedule`, a standard 5-field cron expression read in the Server's time zone (ADR [0079](../../docs/adr/0079-plugins-declare-jobs-and-the-kernel-runs-them-on-cron.md)). [`job.proto`](../../proto/nama/plugin/v1/job.proto) holds `nama.plugin.v1.JobService`, whose one rpc, `Run`, calls the required `run_job` export with a `RunJob` naming the Job and carrying the Kernel's clock as `now_ms`; the Plugin answers `JobRan`. The Kernel refuses a Plugin naming `JobService` with no Jobs, or with a Job whose id repeats or isn't one or more of a-z, 0-9 and `-`, or whose schedule doesn't parse or has a seconds field. While the Plugin is enabled the Kernel runs each Job when its schedule comes due, one Run at a time per Job: a firing due while the Job runs is dropped, and firings missed while the Server was down are not made up. Different Jobs run at once. A Job without a schedule never runs on its own. A Run that returns an error is logged; one that traps or runs past its 60 seconds is also counted toward the crashes in a row, as any export's is.

## The Kernel's functions

During any of its calls, any Plugin, whatever its `points`, may call the Kernel's functions in the Wasm import namespace `nama` (ADR [0071](../../docs/adr/0071-any-plugin-calls-the-kernel-functions-its-permissions-allow.md)); [`automation.proto`](../../proto/nama/plugin/v1/automation.proto) holds their messages. Each takes its request message, encoded, and returns a `KernelAnswer`: `answer` holds the function's response, encoded, and `refused` says in plain words why the Kernel refused, such as a Permission not granted. Each function needs a Plugin `Permission`, which the Manifest requests in `permissions` and the Admin grants when enabling the Plugin; the granted Permissions alone decide which functions answer:

| Function | Takes | Answers | Permission |
| --- | --- | --- | --- |
| `store_get` | `StoreKey` | `StoreValue` | `PERMISSION_STORE` |
| `store_put` | `StoreEntry` | `Stored` | `PERMISSION_STORE` |
| `store_delete` | `StoreKey` | `Stored` | `PERMISSION_STORE` |
| `list_libraries` | `LibrariesAsked` | `Libraries` | `PERMISSION_READ_LIBRARIES` |
| `list_titles` | `TitlesAsked` | `Titles` | `PERMISSION_READ_LIBRARIES` |
| `list_watch_states` | `WatchStatesAsked` | `WatchStates` | `PERMISSION_READ_WATCH_STATES` |
| `list_users` | `UsersAsked` | `Users` | `PERMISSION_READ_USERS` |
| `list_requesters` | `RequestersAsked` | `Requesters` | `PERMISSION_READ_REQUESTS` |
| `list_watchlist` | `WatchlistAsked` | `Watchlist` | `PERMISSION_READ_WATCHLISTS` |
| `delete_media` | `DeleteAsked` | `DeleteStarted` | `PERMISSION_DELETE_MEDIA` |
| `forget_home_rows` | `ForgetHomeRowsAsked` | `HomeRowsForgotten` | `PERMISSION_FORGET_HOME_ROWS` |
| `forget_gone_plugins` | `ForgetGonePluginsAsked` | `GonePluginsForgotten` | `PERMISSION_FORGET_GONE_PLUGINS` |

The functions are not a service of their own: they are not an Extension Point and no Manifest names them, so they are versioned with `CONTRACT_VERSION`. The Kernel refuses a Manifest requesting a `Permission` it doesn't know, or `PERMISSION_UNSPECIFIED`. A Plugin should carry on when a function answers `refused`, as a subtitle source not granted the Store logs in again for each download.

The Store keeps bytes per Plugin under a key of up to 256 bytes, with a value of up to 64 KiB; an entry with `user_id` set belongs to that User. A Plugin keeps at most 10 000 entries, Plugin-wide and per-User together: at that cap the Kernel refuses a new key, though it still replaces the value under a key the Plugin holds. `list_titles` answers a Library's titles by kind and then id, a page of up to `page_size` (at most 1000) at a time, from the `page_token` the page before handed out in `next_page_token`, which is empty on the last; a `page_size` of 0 answers every title at once. A `TitleRef` names a Movie or an Episode in a Library by the `TitleId` its Watch State is kept by. A `Title` holds the Movie's genres and Content Rating, or the Episode's Show's, and an Episode's `show_id`, its Show's id picked as `TitleRef.id` is. `list_watch_states` answers every User's Watch States, or with `WatchStatesAsked.user_id` set only that User's. `Watchlist` holds one User's Watchlist, each title as a `TitleKind` and the `TitleId` it was added under, whether or not a Library has it. `Users` holds every User, with their id and display name only: every User sees every Library, so these are every User who can watch a title, including those without a Watch State. `Requesters` gives each title asked for the ids of the Users who Requested it, never the Request itself: a Movie's through any Request for it that isn't Declined, whatever its state, and an Episode's through any such Request for its Season, with the Requesters of the Followed Show that requested that Season unless it was Declined. `requested` is set when any such Request exists, so a title whose Requesters were all deleted is told from one nobody Requested. `DeleteStarted` means the Kernel checked the delete and it goes on in the background; its `taken_along` holds the other titles that go with it. A file holding two Episodes goes with either, so the Kernel refuses, deleting nothing, a delete that would take along an Episode `DeleteAsked.also` doesn't name, and its refusal names each such Episode. `forget_home_rows` deletes the own Home rows and Featured suggestions of each User who hasn't opened home in at least `days` days, at least 1, and answers how many Users had some. `forget_gone_plugins` deletes the Store entries, settings, Personal settings and Plugin Connections of each Plugin the Server hasn't had, enabled or not, for at least `days` days, at least 1, and answers their ids; the Server has a Plugin from when it finds it until a start or a listing of the Plugins no longer does, and has every Plugin it had while it holds one it refused, since a refused file's id can't be read.

## Title ids

A title's ids reach a Plugin as `repeated TitleId`, each a namespace and a value, defined in [`proto/nama/plugin/v1/request.proto`](../../proto/nama/plugin/v1/request.proto) (ADR [0042](../../docs/adr/0042-a-titles-id-is-a-namespace-and-a-value.md)). A namespace is one or more of a-z and 0-9; a value is never empty. A title has at most one id per namespace, and any one of them identifies it. `tmdb`, `imdb` and `tvdb` are well known, and a Plugin may bring any other. The Kernel never interprets a value, so a Plugin that needs a number parses it itself. `nama_pdk::title_id` reads the value in one namespace.

The Manifest's `movie_id_namespaces` and `show_id_namespaces` (fields 11 and 12 in [`manifest.proto`](../../proto/nama/plugin/v1/manifest.proto)) name the namespaces a `MovieFulfillerService` or `ShowFulfillerService` can find a title by. Any one is enough, and an empty list means any title. The Kernel refuses at load a Manifest naming a malformed namespace there. It never hands such a Fulfiller a Request whose title has none of them: it fails the Request instead, showing the missing namespaces.

## What the Kernel gives a Plugin

The Server sets this up in [`crates/nama-server/src/plugins/wasm/load.rs`](../nama-server/src/plugins/wasm/load.rs), mostly in `compile_with_kernel`. It calls an Installed Plugin in four ways: `manifest()` once, when it loads the Package; `check_settings()` when an admin tests settings, saves settings in which they set a choice setting, or replaces a Fulfiller's Qualities with a non-empty list, refusing the save or replace if it fails; `check_personal_settings()`, if the Plugin exports it, when a User saves their Personal settings, refusing the save if it fails; and the exports of the Extension Points its Manifest names, such as `fulfill`, while it is enabled.

- **A clock.** The function `now` in the Wasm import namespace `nama` takes no arguments and returns an `i64`: the milliseconds since the Unix epoch by the Server's clock. A Plugin needs it because `SystemTime::now()` panics on `wasm32-unknown-unknown`. Every call has it.
- **A Plugin Log.** The function `log` in the namespace `nama` takes an `i32` level, 0 `debug`, 1 `info`, 2 `warn` or 3 `error`, and an `i64`, the offset of an Extism memory block holding the line as UTF-8 text, which the Kernel only reads; it returns nothing. The Server logs the line at that level under the target `nama::plugin`, naming the Plugin, with the values of its secret settings blanked and cut at 2 KiB, marked `[cut]`. A Plugin may write a burst of 50 lines and 10 a second after that; the Server drops the lines over it and, at most once a minute, warns how many it dropped when the Plugin next writes one or is disabled. A line below the level `RUST_LOG` asks for is dropped without counting. `log` doesn't pause the call's clock. A level or block the Kernel can't read drops the line, never a trap. Every call can import it, but in `manifest()`, `check_settings()` and `check_personal_settings()` it drops every line. The Server's log filters drop what a Plugin writes through Extism's own log functions; a `RUST_LOG` that is set replaces stdout's filter, so it should keep `extism::pdk=off`. `nama_pdk::{debug!, info!, warn!, error!}` call it.
- **The Kernel's functions.** `store_get`, `store_put`, `store_delete`, `list_libraries`, `list_titles`, `list_watch_states`, `list_users`, `list_requesters`, `list_watchlist`, `delete_media`, `forget_home_rows` and `forget_gone_plugins`, also in the namespace `nama` and listed under "The Kernel's functions" above. Each takes one `i64` and returns one: the offset of an Extism memory block, as Extism's host functions take and return them. The block passed holds the request message, encoded; the block returned holds a `KernelAnswer`, encoded. A request the Kernel can't read is answered `refused`, never a trap. Every call can import them, so a Plugin calling them still loads, but they answer `refused` in `manifest()`, `check_settings()` and `check_personal_settings()`, which run for no enabled Plugin, and until the Server is serving. The Kernel answers on the thread the call runs on, but the time it spends answering doesn't count toward the call's time limit.
- **128 MiB of memory and 5 seconds per call**, the memory counting the Plugin's own and what Extism keeps for it, the time only the Plugin's own: not the Kernel's answering its calls to the Kernel's functions. A `run_job`, each blob store call and `shared_rows` may run for 60 seconds. A call past either limit fails. What that costs depends on the call: past one, `manifest()` gets the Plugin refused, and `check_settings()` or `check_personal_settings()` fails that check.
- **Three crashes in a row disable the Plugin.** Only an Extension Point's export crashes: when it runs past a limit or traps, not when it returns an error. Each Extension Point counts its own crashes, except that a Movie and a Show Fulfiller count as one.
- **Settings as text.** `check_settings()`, `check_personal_settings()` and the Extension Points' exports find each setting in the Extism config under its key, as text: a bool as `true` or `false`, a number in decimal, a LIBRARIES setting's Library ids in decimal joined by `,` (empty for none). A setting holds what the admin set, or its Manifest default if the admin set nothing; one with neither is not in the config. `check_settings()` gets the settings being tested, which may be unsaved, or being saved; when an admin replaces Qualities, it gets the stored ones. `manifest()` gets no settings. Personal settings are never in the config; see above.
- **HTTP to named hosts only.** A Plugin may send HTTP requests only to the hosts its Manifest's `allowed_hosts` names and the host of each of its URL settings: the saved settings for an Extension Point's exports and `check_personal_settings()`, the settings `check_settings()` is given for that call. `manifest()` may send none.
- **HTTP response headers.** A Plugin gets the headers of each response to its own HTTP requests, such as `Retry-After` or `ratelimit-*` on a 429, so it can keep to an outside service's rate limits (ADR 0067): the Server turns on Extism's `with_http_response_headers`. A header sent more than once reaches it with its last value only, and one whose value isn't visible ASCII not at all. `nama_pdk::Response::header` reads one.

## Generated code is checked in

The code under `src/generated/` is written by `buf generate` and committed, for the reasons in [`crates/nama-proto/README.md`](../nama-proto/README.md). Don't edit it by hand. To regenerate after a schema change, install the tools as that README says, then run `buf generate` in `proto/`; one run writes both crates and the web app's code.
