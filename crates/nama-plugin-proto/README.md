# nama-plugin-proto

Rust types for the Plugin contract, generated from [`proto/nama/plugin/`](../../proto/nama/plugin) (ADR 0041). `nama.plugin.v1` is the module `nama_plugin_proto::nama::plugin::v1`, holding the messages the Kernel and its Installed Plugins exchange, such as the `Manifest`. `nama-pdk` re-exports this crate, so a Plugin depends on `nama-pdk` alone.

`CONTRACT_VERSION` is the Plugin contract's version, which an Installed Plugin's `Manifest.contract` requirement is matched against. It has a number of its own, separate from this crate's version in `Cargo.toml`; `AGENTS.md` says when it changes.

The contract is more than the messages: `CONTRACT_VERSION` also covers what the Kernel gives an Installed Plugin at run time, below.

Each Extension Point an Installed Plugin can serve is a service of the contract, such as `nama.plugin.v1.NotifierService`, whose rpcs name the exports the Kernel calls (ADR 0043). Each has a version of its own, in `SERVICES`; the `services` module holds their full names. A Manifest names the points it serves in `points`, each by its service's full name and a semver requirement on its version.

`nama.plugin.v1.TitleSourceService`, in [`title_source.proto`](../../proto/nama/plugin/v1/title_source.proto), is a title source the Kernel searches and fetches Movies and Shows from to Match a Library's files. Every one of its exports (`title_search`, `title_movie`, `title_show`, `title_season`, `title_episode`, `title_image` and `title_artwork`) is optional: the Kernel asks a source only for the ones it has. Its Manifest names in `title_namespace` the id namespace it keeps titles under, such as `tvdb`, and in `title_lookup_namespaces` any others it can look a title up by, such as `imdb`; the Kernel refuses one naming the service without a well-formed namespace in the first, or with a malformed one in the second. Asked by an id in a namespace it can't use, a source answers with `unsupported_id` set, and the Kernel asks the next source. When it stores a Match, the Kernel asks every source in the Library's order that has `title_artwork` for its artwork list and picks the Poster, Backdrop and Title Logo per kind (ADR 0045).

`nama.plugin.v1.RecogniserService`, in [`recogniser.proto`](../../proto/nama/plugin/v1/recogniser.proto), is a Recogniser: it proposes what a file is or which title an Item names, and the Kernel decides (ADR [0050](../../docs/adr/0050-recognisers-propose-what-a-file-is.md)). Both of its exports are optional, and the Kernel asks a Recogniser only for the ones it has. `recognise_title` is asked about an Item the title sources' search couldn't settle, with its name, its files and the candidates the search found, and answers the title's ids; the Kernel takes them only in a namespace one of the Library's title sources serves, and fetches the title as it would for an ID Hint. `recognise_file` is asked about a file the Kernel's name parser made no Item from, such as an Episode numbered from the start of its Show, and answers a Movie or a Show's Season and Episodes, which the Kernel then Matches as usual. An empty answer means the Recogniser can't tell, and the Kernel asks the next one in the Library's order; a failed export leaves the Item or file undecided until the next Scan. The Kernel owns every Match and the Unmatched decision.

`nama.plugin.v1.BlobStoreService`, in [`blob_store.proto`](../../proto/nama/plugin/v1/blob_store.proto), is a blob store: it keeps the Kernel's own stored files, such as the image store's originals, Custom Images and Plugin logos, and never media files (ADR [0052](../../docs/adr/0052-the-kernels-stored-files-live-in-a-blob-store.md)). All five of its exports are required: `blob_put` stores an object at a key, replacing any there; `blob_get` answers it, with `found` false for a missing key rather than a failure; `blob_delete` deletes it, and succeeds for a missing key; `blob_list` answers a page of at most 1000 keys starting with a prefix, with an empty `next_page_token` on the last; and `blob_exists` says whether an object is at a key. A key is `/`-separated, at most 1024 bytes, of ASCII letters, digits and `-_.%/`. One call carries one object of at most `BLOB_MAX_BYTES`, 20 MiB: the Kernel never puts a larger one, and a Plugin may refuse one. A failed export fails the Kernel's read or write.

`nama.plugin.v1.NotifierService`, in [`notifier.proto`](../../proto/nama/plugin/v1/notifier.proto), delivers notifications about Requests. A `Delivery` goes to the Plugin's own channel, to one User's Plugin Connection, or, for a Plugin whose Manifest declares `personal_settings`, to a `UserRecipient`: a User who set the Plugin's Personal settings, with their values, such as their own webhook or topic.

## Personal settings

A Manifest's `settings` are Plugin-wide: an admin sets them once. Its `personal_settings` (ADR 0046) are settings each User sets for themself. Only the TEXT, SECRET, BOOL and INTEGER kinds are allowed, since a User's value must not widen the hosts a Plugin reaches, and a User can't pick from the Admin's Library list: the Kernel refuses a Plugin with a URL, CHOICE or LIBRARIES Personal setting, or with a key that repeats or that `settings` also names. A Plugin never finds them in its Extism config; the Kernel hands one User's values, as text, only in a call for that User, such as a `Delivery` to `UserRecipient`, or `check_personal_settings()` when that User saves them.

## The Automation lane

In the Automation lane a Plugin asks the Kernel (ADR [0048](../../docs/adr/0048-plugins-automate-through-a-kernel-service.md)). [`automation.proto`](../../proto/nama/plugin/v1/automation.proto) holds its messages and `nama.plugin.v1.AutomationService`, whose one rpc, `Tick`, calls the required `tick` export. On a Plugin's scheduled tick, every `Manifest.tick_every_seconds` (at least 60, and required when `points` names `AutomationService`), the Kernel hands it a `Tick` carrying the Kernel's clock as `now_ms`, which the Plugin uses rather than its own; the Plugin answers `Ticked`. A tick that fails is logged and counted toward the crashes in a row, as an Observer's is. The Kernel refuses a Manifest requesting a `Permission` it doesn't know, or `PERMISSION_UNSPECIFIED`.

During any of its calls, a Plugin whose `points` name `AutomationService` may call the Kernel's functions in the Wasm import namespace `nama`. Each takes its request message, encoded, and returns a `KernelAnswer`: `answer` holds the function's response, encoded, and `refused` says in plain words why the Kernel refused, such as a Permission not granted. Each function needs a Plugin `Permission`, which the Manifest requests in `permissions` and the Admin grants when enabling the Plugin:

| Function | Takes | Answers | Permission |
| --- | --- | --- | --- |
| `store_get` | `StoreKey` | `StoreValue` | `PERMISSION_STORE` |
| `store_put` | `StoreEntry` | `Stored` | `PERMISSION_STORE` |
| `store_delete` | `StoreKey` | `Stored` | `PERMISSION_STORE` |
| `list_libraries` | `LibrariesAsked` | `Libraries` | `PERMISSION_READ_LIBRARIES` |
| `list_titles` | `TitlesAsked` | `Titles` | `PERMISSION_READ_LIBRARIES` |
| `list_watch_states` | `WatchStatesAsked` | `WatchStates` | `PERMISSION_READ_WATCH_STATES` |
| `list_users` | `UsersAsked` | `Users` | `PERMISSION_READ_USERS` |
| `delete_media` | `DeleteAsked` | `DeleteStarted` | `PERMISSION_DELETE_MEDIA` |

The functions are not a service of their own: they are not an Extension Point and no Manifest names them, so they are versioned with `AutomationService`.

The Store keeps bytes per Plugin under a key of up to 256 bytes, with a value of up to 64 KiB; an entry with `user_id` set belongs to that User. A Plugin keeps at most 10 000 entries, Plugin-wide and per-User together: at that cap the Kernel refuses a new key, though it still replaces the value under a key the Plugin holds. `list_titles` answers a Library's titles by kind and then id, a page of up to `page_size` (at most 1000) at a time, from the `page_token` the page before handed out in `next_page_token`, which is empty on the last; a `page_size` of 0 answers every title at once. A `TitleRef` names a Movie or an Episode in a Library by the `TitleId` its Watch State is kept by. `Users` holds every User, with their id and display name only: every User sees every Library, so these are every User a title is for, including those without a Watch State. `DeleteStarted` means the Kernel checked the delete and it goes on in the background; its `taken_along` holds the other titles that go with it. A file holding two Episodes goes with either, so the Kernel refuses, deleting nothing, a delete that would take along an Episode `DeleteAsked.also` doesn't name, and its refusal names each such Episode.

## Versions

The contract crates, `nama-plugin-proto`, `nama-pdk` and `nama-plugin-api`, move together: their version in `Cargo.toml` changes with each release, separately from `CONTRACT_VERSION` and the service versions in `SERVICES`.

- **0.3.0 (unreleased)**: `NotifierService` 1.2.0: for a `UserRecipient` that answers `recipient_gone`, the Kernel deletes that User's Personal settings for the Plugin.
  The Manifest adds `permissions` and `tick_every_seconds`, and `automation.proto` adds the Automation lane's messages, `Permission`, `KernelAnswer` and `AutomationService` 1.0.0.
  `MovieFulfillerService` and `ShowFulfillerService` 1.1.0 add `retry_after_seconds` to `Fulfilled`, `StoppedMonitoring` and `Unfollowed`: a Fulfiller that can't act yet asks the Kernel to ask again after that many seconds.
  `TitleSourceService` 1.2.0 adds `genres` and `content_rating` to `Movie` and `Show`.
  `recogniser.proto` adds `RecogniserService` 1.0.0, a Recogniser proposing what a file is or which title an Item names.
  `AutomationService` 1.1.0 adds the Kernel function `list_users`, answering every User's id and display name, with `UsersAsked`, `Users`, `User` and `PERMISSION_READ_USERS`; pages `list_titles` with `TitlesAsked.page_size` and `page_token` and `Titles.next_page_token`; adds `DeleteAsked.also` and `DeleteStarted.taken_along`, refusing a delete that would take along an Episode `also` doesn't name; and caps a Plugin's Store at 10 000 entries.
  A call's time limit counts only the Plugin's own time, not the Kernel's answering its functions, and a `tick` may run for 60 seconds rather than 5.
  `CONTRACT_VERSION` 0.4.0: `blob_store.proto` adds `BlobStoreService` 1.0.0, a blob store keeping the Kernel's own stored files, with `BLOB_MAX_BYTES`; a blob store call may run for 60 seconds. `SETTING_KIND_LIBRARIES` and `SettingValue.library_ids` (`LibraryIds`) add a setting naming Libraries by id, which an admin picks from the Server's Library list; the Kernel refuses saving an id no Library has, and a Plugin skips an id the Kernel no longer lists (ADR 0053).
  `CONTRACT_VERSION` 0.4.1: the optional `check_personal_settings()` export, taking `PersonalSettingsCheck` and returning `PersonalSettingsChecked`, checks a User's Personal settings when they save them, and the Kernel refuses the save if it fails.
  `CONTRACT_VERSION` 0.4.2: `Playback.plan_id` names the Playback Plan a Playback event is about, pairing its `PlaybackStarted` with its `PlaybackEnded`; ids start again when the Server restarts.
- **0.2.0**: `TitleSourceService` 1.1.0 adds `Manifest.title_lookup_namespaces`, the `unsupported_id` answers and the `Artwork` rpc with `ArtworkAsked`, `ArtworkAnswer`, `Artwork` and `ArtworkKind`. `NotifierService` 1.1.0 adds `UserRecipient`, and the Manifest adds `personal_settings`.

## Title ids

A title's ids reach a Plugin as `repeated TitleId`, each a namespace and a value, defined in [`proto/nama/plugin/v1/request.proto`](../../proto/nama/plugin/v1/request.proto) (ADR [0042](../../docs/adr/0042-a-titles-id-is-a-namespace-and-a-value.md)). A namespace is one or more of a-z and 0-9; a value is never empty. A title has at most one id per namespace, and any one of them identifies it. `tmdb`, `imdb` and `tvdb` are well known, and a Plugin may bring any other. The Kernel never interprets a value, so a Plugin that needs a number parses it itself. `nama_pdk::title_id` reads the value in one namespace.

The Manifest's `movie_id_namespaces` and `show_id_namespaces` (fields 11 and 12 in [`manifest.proto`](../../proto/nama/plugin/v1/manifest.proto)) name the namespaces a `MovieFulfillerService` or `ShowFulfillerService` can find a title by. Any one is enough, and an empty list means any title. The Kernel refuses at load a Manifest naming a malformed namespace there. It never hands such a Fulfiller a Request whose title has none of them: it fails the Request instead, showing the missing namespaces.

## What the Kernel gives a Plugin

The Server sets this up in [`crates/nama-server/src/plugins/wasm/load.rs`](../nama-server/src/plugins/wasm/load.rs), mostly in `compile_with_kernel`. It calls an Installed Plugin in four ways: `manifest()` once, when it loads the Package; `check_settings()` when an admin tests settings; `check_personal_settings()`, if the Plugin exports it, when a User saves their Personal settings, the one call outside a Delivery that hands it Personal settings, refusing the save if it fails; and the exports of the Extension Points its Manifest names, such as `fulfill`, while it is enabled.

- **A clock.** The function `now` in the Wasm import namespace `nama` takes no arguments and returns an `i64`: the milliseconds since the Unix epoch by the Server's clock. A Plugin needs it because `SystemTime::now()` panics on `wasm32-unknown-unknown`. Every call has it.
- **The Kernel's functions.** `store_get`, `store_put`, `store_delete`, `list_libraries`, `list_titles`, `list_watch_states`, `list_users` and `delete_media`, also in the namespace `nama` and listed under "The Automation lane" above. Each takes one `i64` and returns one: the offset of an Extism memory block, as Extism's host functions take and return them. The block passed holds the request message, encoded; the block returned holds a `KernelAnswer`, encoded. A request the Kernel can't read is answered `refused`, never a trap. Every call can import them, so a Plugin calling them still loads, but they answer `refused` in `manifest()`, `check_settings()` and `check_personal_settings()`, which run for no enabled Plugin, and until the Server is serving. The Kernel answers on the thread the call runs on, but the time it spends answering doesn't count toward the call's time limit.
- **128 MiB of memory and 5 seconds per call**, the memory counting the Plugin's own and what Extism keeps for it, the time only the Plugin's own: not the Kernel's answering its calls to the Kernel's functions. A `tick`, and each blob store call, may run for 60 seconds. A call past either limit fails. What that costs depends on the call: past one, `manifest()` gets the Plugin refused, and `check_settings()` or `check_personal_settings()` fails that check.
- **Three crashes in a row disable the Plugin.** Only an Extension Point's export crashes: when it runs past a limit or traps, not when it returns an error. Each Extension Point counts its own crashes, except that a Movie and a Show Fulfiller count as one.
- **Settings as text.** `check_settings()`, `check_personal_settings()` and the Extension Points' exports find each setting in the Extism config under its key, as text: a bool as `true` or `false`, a number in decimal, a LIBRARIES setting's Library ids in decimal joined by `,` (empty for none). A setting holds what the admin set, or its Manifest default if the admin set nothing; one with neither is not in the config. `check_settings()` gets the settings being tested, which may be unsaved. `manifest()` gets no settings. Personal settings are never in the config; see above.
- **HTTP to named hosts only.** A Plugin may send HTTP requests only to the hosts its Manifest's `allowed_hosts` names and the host of each of its URL settings: the saved settings for an Extension Point's exports and `check_personal_settings()`, the settings being tested for `check_settings()`. `manifest()` may send none.
- **No HTTP response headers.** The Kernel doesn't pass a response's headers to the Plugin: `compile_with_kernel` leaves Extism's `with_http_response_headers` off.

## Generated code is checked in

The code under `src/generated/` is written by `buf generate` and committed, for the reasons in [`crates/nama-proto/README.md`](../nama-proto/README.md). Don't edit it by hand. To regenerate after a schema change, install the tools as that README says, then run `buf generate` in `proto/`; one run writes both crates and the web app's code.
