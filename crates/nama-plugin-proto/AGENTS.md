## nama-plugin-proto

- Never edit `src/generated/` by hand, and never let rustfmt touch it. Change the schema in `proto/nama/plugin/`, then run `buf generate` in `proto/`. See `README.md`.
- The contract imports nothing from the client API, `proto/nama/v1/` (ADR 0041). `tests/stands_alone.rs` checks it.
- A change under `proto/nama/plugin/` needs no entry in `proto/BREAKING.md`; `CONTRACT_VERSION` or a service's version covers it.
- `CONTRACT_VERSION` in `src/lib.rs` changes with what an Installed Plugin sees, not with this crate's version in `Cargo.toml`. While it is 0.x, a change a Plugin built before can't work with bumps the minor, a change that only adds something a Plugin may use bumps the patch, and a change Plugins can't see bumps nothing. Changes that land on main together take one bump.
- Each service in `SERVICES` in `src/lib.rs` has a version of its own, which changes by the `CONTRACT_VERSION` rule's terms with what that service's Plugins see: its rpcs, the messages only it takes or returns, and what the Kernel does with them. Being 1.x, a change a Plugin built before can't work with bumps the major, and one that only adds something bumps the minor. `CONTRACT_VERSION` still covers the Manifest, the messages more than one service shares and what the Kernel gives a Plugin. A new service joins `SERVICES` and the `services` module at 1.0.0 (ADR 0043).
- A change to what the Kernel gives a Plugin (the `nama` functions, the limits on a call, how settings and HTTP reach it) updates the README's "What the Kernel gives a Plugin" section and follows the `CONTRACT_VERSION` rule above.
- A Kernel function is one row in `kernel_functions!` in `src/lib.rs`, giving its name, its messages and its Plugin Permission. The Server, `nama-plugin-api` and `nama-pdk` read it, and `tests/functions.rs` pins `automation.proto`'s comment and the README to it.
