## Links

Links (GLOSSARY.md): registering a Server through an OAuth device flow (ADR 0011), its credential, its Server Addresses, Unlinking, and the tokens signed for Servers (ADR 0099); Linking a Linked Server's Users to Accounts (`users.rs`), Users created from an Account (`invites.rs`), and signing in to a Linked Server with an Account (`server_sign_ins.rs`).

- **One owner.** Only this area reads or writes `linked_servers`, `server_link_codes`, `user_links`, `user_link_codes`, `user_invites` and `server_sign_ins`, tests included.
- **The Server polls; the Hub never calls it**, but to check its public port. A Server starts with a device code it keeps and a code a person enters. Entering it makes the Linked Server; the Server's next poll collects its credential and deletes the codes. A Server Linking by redirect also gives the address approving its code sends the person back to (ADR 0105). The Hub checks only that it's an `http` or `https` URL, as it has no Server Addresses for a Server not Linked yet; the Server checks it is one of its own.
- **Credentials are opaque** (ADR 0098): 32 random bytes, stored only as their SHA-256 hash, revoked by deleting the row. The token a Server gets with it, so it can check which Account it is Linked to, the token it shows a Relay, naming its own name, and the tokens naming one of its Users for a sign-in, are the only things signed.
- **A User Links like a Server**, but their Server asks with its credential, so a User's code needs no device code: the Server asks `GetUserLink` until it is entered. A User Links to one Account, and an Account to one User on each of many Servers, so signing in with it names one User and its one Watch State is theirs (#2045). Unlinking a Server Unlinks its Users.
- **Server Addresses come from the Server**, which reports them as they change. The Hub keeps only the last ones, and checks each is an `http` or `https` URL, since its pages link to them. Clients reach Servers there themselves: the Hub never proxies a call or media (ADR 0094).
- **The public port is checked where the report came from** (ADR 0057): the Hub opens a TCP connection to the request's own IP address, never one the Server names, so a Server can't have the Hub call anyone else, and sends nothing on it. Addresses go best first: the Server URL, the public address only if reached, the Relay's, then the LAN ones.
- **Names follow the reports** (ADR 0104, `names.rs`): each report stores its addresses, replaces the records under the Server's own name, its id in hex, then removes them again if the Server was Unlinked meanwhile. A Server's certificate challenge goes as TXT records at `_acme-challenge.<own name>`, only its own. Unlinking removes them all before and after deleting the row, and fails while it can't. No transaction is held across a DNS provider's call. Only a private IPv4 LAN address gets a name, and the Relay the Server names gets `relay.<own name>`.
- **Only a proven email Links** (ADR 0100), Servers and Users alike, accepting a User created from the Account included, and only from a session with Recent Authentication. `may_link` alone decides it: an unproven email is refused as `EmailNotProven`, which asks for a Sign-in Link, only on a Hub that sends them, and as `SignInLinksOff` on one without mail.
- **Inviting reveals nothing** (ADR 0092): asking an email with no Account answers as one with an Account does.
- **A sign-in is a device flow too.** The Server polls with a device code it got over its credential; the Account approves on the page for the sign-in's id. The token names the User through their Link, `aud` the Linked Server, and is handed out once. The return address must be on one of the Server's Server Addresses, and approving adds a one-time code to it that the Server's first poll after must bring, so only the browser sent back there finishes (#1934).
- **A Server token skips the flow** (ADR 0105): the web app at the Hub asks for a token naming the Account's User on one Linked Server, signed only while the Account has a User Linked there, and trades it at that Server for a Device. It passes through the browser, so it carries a random `jti` the Server takes once. It carries the session's sign-in time as `auth_time`, from which the Server gives the Device Recent Authentication.
- **A batch keeps only Linked Users' items.** A Linked Server's push or Viewing Events name many Users, and `linked_accounts` pairs each item with its User's Account in one query, leaving out, not refusing, those of a User who isn't Linked, so a Server's queue empties after an Unlink.
- **Scoped by Account** (ADR 0097): an Account lists only the Linked Servers it owns or has a User on, lists and Unlinks only its own Linked Users, and a Linked Server Unlinks only itself and its own Users.

### Neighbours

- Uses: `accounts` (an `AccountSession`'s proven email, when it signed in and its Recent Authentication check, whose error `links` passes on, whether the Hub sends Sign-in Links, an Account's email, the Account with an email, deleting an Account), `signing` (the token) and `dns` (the Server's names).
- Used by: `api`, whose auth layer turns a bearer credential into a `LinkedServer`, and which converts what `links.rs` re-exports, and `diagnostics` (`LinkedServerId`, each Server's volume).
- Used by: `sync`, `viewing` and `recommendations`, handed it by `api`, for the Accounts a Linked Server's Users are Linked to.
